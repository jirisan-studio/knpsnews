# KNPSNEWS 개발 프로젝트 — 마스터 지시문

국립공원공단 직원이 실제 업무에서 사용할 수 있는 모바일 중심의 뉴스 아카이브 웹서비스 `knpsnews`를 구축한다.

이 프로젝트는 이미 기획 및 기본 설계를 완료한 상태다.
아래 요구사항을 프로젝트의 기준 명세로 삼고 실제 구현을 시작하라.

기획을 임의로 변경하거나 기능을 임의로 추가하지 말고, 안정적으로 동작하는 MVP를 단계별로 완성하는 것을 최우선 목표로 한다.

2. 프로젝트 목적
==================================================

현재 국립공원공단에서는 홍보 관련 부서가 전날의 주요 언론보도를 취합해 직원에게 전달하고 있으며,
직원은 PDF 등을 직접 열어서 기사를 확인해야 한다.

KNPSNEWS의 목적은 이러한 불편을 개선하여 직원이 휴대폰에서 사이트에 접속하는 것만으로 국립공원 및 공단 관련 뉴스를 빠르게 확인할 수 있도록 하는 것이다.

단순한 뉴스 검색 사이트가 아니라,

"국립공원공단 업무 관점으로 뉴스가 축적되고 검색되는 언론보도 아카이브"

를 구축한다.

핵심 검색 개념은 다음 세 가지다.

날짜 × 뉴스 관심영역 × 키워드

예:

2026-10-03 + 지리산

2026-09-01 ~ 2026-09-30 + 설악산 + 산불

전체기간 + 야생생물보전원 + 반달가슴곰


==================================================
3. 가장 중요한 초기 데이터 기준
==================================================

과거 뉴스 초기 수집 시작일은 반드시

2026-09-01

로 한다.

기존에 검토했던 "최근 10~14일" 기준은 사용하지 않는다.

서비스 최초 구축 시 가능한 범위에서 NAVER 뉴스 API를 이용하여

2026-09-01 ~ 현재

뉴스를 초기 적재한다.

NAVER API의 검색결과 한계 등으로 특정 기간의 모든 기사를 완벽하게 복원할 수 없는 경우 이를 숨기지 말고 알려준다.

초기 데이터 적재가 끝난 이후부터는 신규 뉴스를 정기적으로 자동 수집하여 DB에 계속 축적한다.

==================================================

공식 조직도를 그대로 뉴스 분류체계로 사용하지 않는다.

별도의

News Area
또는
뉴스 관심영역

개념을 사용한다.

뉴스를 찾는 직원의 관점에서 분류한다.


예:

국립공원

- 지리산
- 설악산
- 북한산
- 태안해안
- 한려해상
- 다도해해상
- 기타 국립공원


전문기관

- 국립공원연구원
- 야생생물보전원


생태탐방원

- 북한산생태탐방원
- 지리산생태탐방원
- 기타 생태탐방원


정확한 전체 관심영역 목록은 구현 과정에서 확정할 수 있도록 데이터 기반으로 관리한다.

코드에 하드코딩하지 않는 것을 원칙으로 한다.


==================================================
7. 지리산 처리 원칙
==================================================

공식 조직에서는 지리산 관련 사무소가 지역별로 나뉘어 있지만 뉴스 사용자에게는 기본적으로

"지리산"

하나의 관심영역으로 제공한다.

DB 내부에서는 필요한 경우

지리산
 ├ 지리산경남
 ├ 지리산전남
 └ 지리산전북

처럼 parent-child 관계를 사용할 수 있다.

사용자는 기본적으로 "지리산"을 선택하면 세 지역을 모두 포함한 결과를 본다.

향후 필요하면 세부 필터를 추가할 수 있도록 구조만 준비한다.


==================================================
8. 하나의 기사는 여러 관심영역에 속할 수 있다
==================================================

기사와 관심영역을 1:1로 설계하지 않는다.

예:

"지리산 반달가슴곰 복원사업 관련 기사"

는 동시에

지리산
야생생물보전원

과 관련될 수 있다.

따라서 article과 news_area는 many-to-many 관계로 설계한다.

==================================================
11. 뉴스 자동수집 구조
==================================================

사용자가 사이트에 접속할 때마다 NAVER 뉴스 API를 직접 호출하지 않는다.

다음 구조를 사용한다.

NAVER 뉴스 API
↓
서버 측 뉴스 수집
↓
데이터 정리
↓
중복검사
↓
Supabase 저장
↓
사용자는 Supabase에 저장된 뉴스 조회

즉,

뉴스 수집

과

뉴스 조회

를 분리한다.

NAVER API에 장애가 발생해도 이미 저장된 뉴스는 정상적으로 볼 수 있어야 한다.


==================================================
12. 중복 기사 처리
==================================================

하나의 뉴스가 여러 검색어에서 검색될 수 있다.

예:

지리산
반달가슴곰
국립공원

세 검색어에서 동일 기사가 검색될 수 있다.

동일 기사를 DB에 여러 번 저장하지 않는다.

우선적으로 URL을 기준으로 중복 제거한다.

필요하다면

정규화한 제목
+
언론사
+
발행일

등을 보조 기준으로 사용할 수 있다.

DB 수준에서도 가능한 중복 방지 제약조건을 검토한다.

==================================================
17. 보안 원칙
==================================================

이 항목은 반드시 준수한다.

NAVER Client Secret을 클라이언트에 노출하지 않는다.

Supabase Service Role Key를 클라이언트에 노출하지 않는다.

GitHub Repository에 Secret을 commit하지 않는다.

.env.local을 Git에 올리지 않는다.

Secret은 Vercel Environment Variables로 관리한다.

뉴스 API 호출은 서버 측에서 수행한다.

DB 변경 작업도 가능한 한 서버 측에서 수행한다.

Supabase RLS를 활성화한다.

일반 사용자는 원칙적으로 뉴스 조회만 가능하게 한다.

일반 브라우저에서 INSERT / UPDATE / DELETE 권한을 주지 않는다.


==================================================
18. Supabase 현재 보안 설정
==================================================

프로젝트 생성 시 다음 방향으로 설정했다.

Enable Data API:
ON

Automatically expose new tables:
OFF

Enable automatic RLS:
ON

따라서 필요한 schema/table API 노출 및 RLS 정책을 명시적으로 구성하라.

무조건 RLS를 해제하는 방식으로 문제를 해결하지 않는다.

==================================================
21. 매우 중요한 회귀 방지 원칙
==================================================

앞 단계에서 정상적으로 작동하는 기능을 다음 단계 구현 과정에서 임의로 삭제하거나 변경하지 않는다.

새 기능 추가 전에 현재 상태를 확인한다.

새 기능 구현 후 기존 기능도 다시 테스트한다.

UI를 수정하는 과정에서 기존 기능을 누락시키지 않는다.

DB schema 변경 시 기존 데이터가 손실되지 않도록 한다.

대규모 리팩터링은 특별한 이유가 없는 한 피한다.


==================================================
22. 디자인 변경 원칙
==================================================

바이브코딩 과정에서 요청할 때마다 전체 디자인을 새로 만드는 것을 금지한다.

초기 디자인 시스템을 한번 정한 뒤 유지한다.

새 기능은 기존 UI 언어와 레이아웃을 유지하면서 추가한다.

기능 요청을 받았다고 해서 관계없는 페이지의 디자인을 변경하지 않는다.

사용자가 명시적으로 디자인 변경을 요청한 경우에만 전체 디자인을 수정한다.


==================================================
23. 자동수집
==================================================

초기 목표는 하루 수 회 자동수집이다.

예:

06:00
09:00
12:00
15:00
18:00
21:00

정확한 스케줄은 Vercel 및 사용 가능한 Cron 환경의 제약과 무료/유료 정책을 확인한 후 합리적으로 결정한다.

필요 이상의 API 호출은 하지 않는다.


==================================================
24. 관리자 기능
==================================================

1차 버전에서는 관리자 페이지를 복잡하게 만들 필요가 없다.

가능하다면 다음 정도만 제공한다.

마지막 뉴스 수집시간

최근 수집 성공/실패

오늘 수집된 기사 수

활성 검색어 확인

검색어 활성/비활성

수동 뉴스 수집 실행


단, 관리자 기능을 일반 사용자에게 공개하지 않는다.

인증 없이 위험한 서버 작업을 실행할 수 있는 API endpoint를 만들지 않는다.


==================================================
25. 장애 처리
==================================================

NAVER API 호출 실패 시 기존 서비스가 중단되어서는 안 된다.

예:

NAVER API 오류
↓
수집 실패 로그
↓
기존 DB 뉴스는 계속 정상 제공
↓
다음 수집 때 재시도

수집 과정에서 특정 검색어 하나가 실패하더라도 전체 수집 작업이 모두 실패하지 않도록 가능한 범위에서 처리한다.

26. PWA
==================================================

1차 핵심 기능이 안정된 이후 어렵지 않다면 PWA 형태를 적용한다.

하여 앱처럼 실행할 수 있는 것을 목표로 한다.

단, PWA 때문에 핵심 MVP 개발이 지연되면 후순위로 둔다.


==================================================
27. 성능
==================================================

사용자가 사이트를 열 때 NAVER API 결과를 기다리게 하지 않는다.

이미 Supabase에 저장된 뉴스를 빠르게 보여준다.

뉴스 목록에는 pagination 또는 적절한 incremental loading을 적용하여 수천/수만 건이 쌓여도 한 번에 전체 데이터를 가져오지 않는다.

검색에 필요한 DB index도 고려한다.

38. 최종 원칙
==================================================

이 프로젝트의 목표는 화려한 데모를 만드는 것이 아니다.

국립공원공단 직원이 실제 휴대폰에서 매일 사용할 수 있는

빠르고
단순하고
안정적이며
검색이 편한

뉴스 아카이브를 만드는 것이다.

기술적으로 멋진 기능보다 실제 업무 사용성을 우선한다.

이 명세를 프로젝트의 기준점으로 유지하면서 실제 구축을 시작하라.

현재 준비 상태:

- GitHub Repository: jirisan-studio/knpsnews
- 로컬 프로젝트 경로: D:\Projects\KnpsNews
- GitHub 저장소를 로컬에 Clone 완료
- main 브랜치
- VS Code에서 knpsnews 폴더를 열어둔 상태
- 아직 Next.js 프로젝트는 생성하지 않음

여기서부터 실제 개발을 시작해줘.

먼저 현재 repository의 파일과 상태를 직접 확인하고,
기존 파일을 임의로 삭제하거나 덮어쓰지 말고
마스터 지시문의 STEP 1부터 순서대로 진행해줘.

가능한 작업은 Work에서 직접 수행하고,
내가 직접 해야 하는 작업이 발생할 때만 정확한 방법을 안내해줘.

한꺼번에 모든 기능을 구현하지 말고,
각 단계마다 실행 및 테스트를 통해 정상 작동을 확인한 후 다음 단계로 넘어가줘.
